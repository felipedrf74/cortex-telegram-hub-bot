Nexus application disaster recovery
===================================

Status and boundary
-------------------

Quarterly restore-drill readiness is MANUAL_REQUIRED. The repository contains
a fail-closed isolated boot/smoke/stop implementation, but repository presence
is not site readiness. `restore-readiness.json` is the machine-readable status.
Do not claim quarterly restore readiness until the assets, dedicated nologin
account, provider controls, and off-host age identity are provisioned and one
complete drill has produced retained evidence.

These are installation templates. Adding them to the repository does not
install a timer, create a bucket, upload data, delete backups, restore data, or
change production. Installation and every restore remain owner-authorized
operations. The restore drill is intentionally incapable of applying anything
to the production path.

The application DR boundary is separate from SonarQube backup. It covers:

1. the live Nexus SQLite database through SQLite's online backup API;
2. each local v*.tar.gz exact-release rollback bundle; and
3. a quarterly isolated release-plus-database boot and smoke proof.

Object-store preparation
------------------------

Create a private object-store bucket reachable only over HTTPS. For
`aws-s3:versioned-s3`, grant the ServerDominguez identity only prefix-scoped
`s3:ListBucketVersions`, object Get/Head/Put, `s3:DeleteObjectVersion`, and the
narrowly scoped GetObjectRetention/PutObjectRetention actions required for
release objects. Scope `s3:ListBucketVersions` to the configured
NEXUS_DR_S3_PREFIX and `s3:DeleteObjectVersion` to objects below that prefix;
the AWS retention path does not require unversioned `DeleteObject`. The
approved R2 variance instead retains its existing prefix-scoped ListBucket and
object Get/Head/Put/Delete permissions because R2 has no S3 versions. Deny
plaintext transport in either mode.

The default control mode is `aws-s3:versioned-s3`: bucket versioning must be
enabled and release objects must have S3 Object Lock coverage for at least 90
days. Do not apply the 90-day release lock to database/ because its four
count-based tiers intentionally expire sooner.

Cloudflare R2 does not satisfy the versioned-S3 control. It may be used only as
the explicit `cloudflare-r2:r2-approved-variance`: retain owner approval for
the missing versioning control and enable a Cloudflare bucket lock on exactly
`<NEXUS_DR_S3_PREFIX>/releases/` for at least 90 days. The database count-based
tiers remain outside that lock. Never label R2 versioned or silently select the
variance from the endpoint.

Record the observed provider controls in
`/etc/nexus-application-dr/storage-control-evidence.json`, root:root mode 0600.
The verificationReference is a bounded identifier for a private provider
control-plane export or screenshot; do not put credentials, URLs with tokens,
or raw private evidence in this JSON. Refresh the control observation at least
every 30 days. The exact versioned-S3 shape is:

  {
    "schema": "nexus.application-dr-storage-controls.v1",
    "provider": "aws-s3",
    "controlMode": "versioned-s3",
    "endpoint": "<exact configured HTTPS endpoint>",
    "bucket": "<exact configured bucket>",
    "prefix": "<exact configured prefix>",
    "verifiedAt": "YYYY-MM-DDTHH:MM:SSZ",
    "verificationReference": "private-evidence:s3-controls-YYYYMMDD",
    "versioning": {"supported": true, "status": "enabled"},
    "releasePrefixLock": {
      "control": "s3-object-lock",
      "status": "enabled",
      "prefix": "<exact configured prefix>/releases/",
      "retentionDays": 90
    }
  }

The exact R2 variance shape adds the governed approval:

  {
    "schema": "nexus.application-dr-storage-controls.v1",
    "provider": "cloudflare-r2",
    "controlMode": "r2-approved-variance",
    "endpoint": "<exact configured HTTPS R2 endpoint>",
    "bucket": "<exact configured bucket>",
    "prefix": "<exact configured prefix>",
    "verifiedAt": "YYYY-MM-DDTHH:MM:SSZ",
    "verificationReference": "private-evidence:r2-bucket-lock-YYYYMMDD",
    "versioning": {"supported": false, "status": "not-supported"},
    "releasePrefixLock": {
      "control": "cloudflare-r2-prefix-lock",
      "status": "enabled",
      "prefix": "<exact configured prefix>/releases/",
      "retentionDays": 90
    },
    "varianceApproval": {
      "approvedBy": "owner",
      "approvedAt": "YYYY-MM-DDTHH:MM:SSZ",
      "reason": "r2-has-no-s3-versioning"
    }
  }

Generate the age identity off-host. Put only its public age1... recipient in
backup.env. Keep the private identity in a separate recovery vault and copy it
to an isolated drill host only for a drill. S3 server-side encryption may be
enabled as defense in depth; age client-side encryption is mandatory and
happens before the first upload.

Install in an approved maintenance window
-----------------------------------------

1. Install age, AWS CLI v2, the release-locked root-owned Node runtime, Python
   3.12, curl, GNU coreutils, util-linux, and iproute2 from the approved host
   package source. The backup and restore commands fail if a required tool is
   absent.
2. From the same root-owned, non-group/world-writable reviewed source tree used
   by the promotion bootstrap, run:

     sudo <reviewed-root>/scripts/application-dr-systemd-install.sh \
       <reviewed-root>

   The transactional installer validates `install-layout.tsv`, installs every
   exact asset with its declared root owner/mode, creates the private
   `nexus-drill` nologin account without supplementary groups, and preserves
   the timer's prior enabled/active state. It rolls back partial file and
   account changes on failure. Do not copy these files manually or run the
   installer from an application-user-writable checkout. The promotion
   bootstrap invokes this same installer first so its worker and DR interface
   cannot drift. A host interruption leaves the durable root-only
   `/var/lib/nexus-application-dr/install-in-progress.v1` marker in place.
   The backup unit and direct backup command then fail closed; rerun the same
   reviewed installer to replace the complete compatibility set and clear the
   marker.
3. Create /etc/nexus-application-dr/backup.env from backup.env.example and the
   provider control evidence described above, both root:root mode 0600. Use
   real scoped credentials or an instance-role based provider; never commit
   credentials, private provider evidence, or the age private identity.
4. Confirm the configured database is a canonical, application-user-owned
   regular file with mode 0600, 0640, or 0660. Confirm the rollback directory is
   canonical, application-user-owned mode 0700 and its v*.tar.gz files are mode
   0600. Remediate permissions deliberately; do not relax script validation.
5. Run the following before enabling the timer:

     sudo systemd-tmpfiles --create
     sudo /usr/local/libexec/nexus-application-dr/application-dr-backup.sh \
       --config /etc/nexus-application-dr/backup.env --verify-config
     sudo systemctl daemon-reload
     sudo systemctl enable --now nexus-application-dr-backup.timer

6. Run one owner-observed service invocation, inspect its journal, and verify
   the four database objects and every current release rollback object through
   a read-only bucket listing. Alert on a failed service or a timer whose last
   successful invocation is more than one hour old.

Backup and retention behavior
-----------------------------

The hourly service is a sequential one-shot task. A non-blocking lock prevents
overlap; a second invocation fails visibly. The snapshot is taken near minute
05 of every UTC hour and the unit has a 50-minute deadline. Missing or delayed
runs are failures, not silently accepted RPO exceptions.

The service creates and integrity-checks a transactionally consistent SQLite
snapshot while Nexus remains online. It encrypts the snapshot in a root-only
temporary directory, deletes plaintext, uploads the same encrypted point to
four governed tiers, verifies remote size/digest metadata, and then applies:

  database/hourly   latest 24 hourly keys
  database/daily    latest 7 UTC-date keys
  database/weekly   latest 4 ISO-week keys
  database/monthly  latest 6 UTC-month keys

Daily, weekly, and monthly keys are refreshed by each successful hourly run,
so the retained key holds the newest point for its period. In
`aws-s3:versioned-s3`, retention explicitly exhausts direct 1,000-entry
`ListObjectVersions` pages with the paired key/version markers; AWS CLI
auto-pagination is disabled. The root-owned version-retention helper validates
the complete `NexusApplicationDrVersionListingV1` page envelope and emits an
ordered exact key-plus-VersionId plan. The service deletes one version at a
time in plan order and stops at the first failure. This retains one current
version for each governed retained database key and removes older governed
versions/delete markers without issuing an unversioned delete. Unexpected
objects are never deleted.

The approved R2 variance deliberately keeps the visible-object
ListObjectsV2/DeleteObject algorithm because R2 cannot provide S3 version
identities. Do not reuse that variance path for AWS.

The same invocation scans every current v*.tar.gz bundle in the existing local
rollback directory, verifies ownership/mode and tar readability, encrypts each
previously unseen exact digest, and uploads it under releases/. Cloud escrow is
kept for 90 days plus a 3,600-second deletion grace.

Promotion also creates two transaction-bound candidate recovery objects:
`+escrow-<transaction-id>+phase-pre-mutation...` before PM2/data mutation and
`+escrow-<transaction-id>+phase-post-soak...` after candidate availability and
the 60-second soak. They bind the same runtime, artifact, installed-tree,
recovery-runtime, release-manifest, and staging-attestation identities, but
must use distinct object keys and newly encrypted ciphertext. Each phase
records `escrowId`, `escrowPhase`, plaintext/encrypted SHA-256, encrypted byte
size, `confirmedAt`, `retainUntil`, and the exact AWS `objectVersionId`. AWS
requires `retainUntil` to be at least 90 days after `confirmedAt`. R2 emits null
for unavailable deadline/version fields and explicitly records
`retentionVariance: r2-approved-variance` plus
`approvedUnversionedVariance: true`.

Each exact key/version pair is protected from its creating invocation's
retention plan and re-HEADed and re-downloaded by exact AWS VersionId. The
pre-mutation recovery object is accompanied by a fresh database encrypted
identity/version before cutover. The post-soak object is accompanied by a new
database encrypted identity/version, and candidate readiness is recorded both
before and after those post-soak uploads. The promotion transaction also
requires positive off-host confirmation for its predecessor rollback-bundle
digest before that bundle is eligible for local count pruning. The existing
local policy keeps the latest ten bundles, while the hourly service reconciles
and re-verifies the whole retained set. A failed escrow remains visible and the
unconfirmed bundle must stay local; operators must never prune it merely to
satisfy the count.

Quarterly isolated restore drill
--------------------------------

Prefer a separate recovery host. If that is impossible, run only in an
owner-approved low-load window on ServerDominguez. The supported root-owned
harness uses private network, mount, and PID namespaces; shadows host home and
temporary paths; remounts the host root read-only; drops every capability; and
runs the restored backend as the dedicated nologin account. It refuses a live
path, a host-visible listener, inherited connector credentials, provider/model
access, local authentication bypass, or an unverified process identity.

The installed harness receives one of boot, smoke, or stop plus the absolute
scratch runtime as argv[2], and these mandatory environment values:

  NEXUS_DRILL_MODE=isolated-restore
  NEXUS_DRILL_ROOT=<private scratch exact-release tree>
  NEXUS_DRILL_DATABASE_PATH=<scratch tree>/data/bot.db
  NEXUS_DRILL_BASE_URL=http://127.0.0.1:<dedicated high port>
  NEXUS_DRILL_STATE_DIR=<private application DR state>
  NEXUS_DRILL_USER=<dedicated nologin user>
  NEXUS_DRILL_NODE_BIN=<root-owned release-locked Node>
  NEXUS_DRILL_PYTHON_BIN=<root-owned Python 3.12>

Before boot, the restore command verifies and installs the Node archive and
Python wheelhouse embedded in the exact release. Installation runs as the
dedicated account, with no inherited credentials, in a private network
namespace and with pip `--no-index`; it neither reuses production dependencies
nor downloads packages. The smoke proves connected restored SQLite health,
rejects an invalid bearer token, accepts only the one-use read token, checks
the exact release snapshot, and compares a representative API read with the
restored database. stop validates the exact recorded process and terminates
only its process group; it is idempotent.

Select the newest exact keys by read-only listing under database/hourly/ and
releases/. Then run, with a freshly copied root:root mode-0600 age identity:

  sudo /usr/local/libexec/nexus-application-dr/application-dr-restore-drill.sh \
    --config /etc/nexus-application-dr/backup.env \
    --database-key '<exact newest hourly key>' \
    --database-version-id '<exact retained AWS VersionId>' \
    --release-key '<exact compatible release escrow key>' \
    --release-version-id '<exact retained AWS VersionId>' \
    --identity-file /run/nexus-dr-age-identity \
    --output /var/lib/nexus-application-dr/evidence/quarterly-YYYYQn.json

For AWS, obtain both VersionIds from retained private backup evidence or an
exact read-only version listing; the drill HEADs and downloads only those
versions. Omit both version arguments for the approved R2 variance. The command
cross-binds the recovery key, original filename, and plaintext SHA-256; enforces
bounded HEAD/range-download sizes and scratch capacity; verifies encrypted and
plaintext SHA-256 values, SQLite integrity/foreign keys, hostile archive paths,
and the signed exact-runtime inventory; and runs all reconstructed dependency
code only as the dedicated nologin account in a private no-network namespace.

Before boot it permits only an exact governed migration prefix. After the
isolated processes stop, it takes a fresh SQLite online-backup snapshot so any
committed WAL state is included, repeats integrity/foreign-key validation, and
requires the exact terminal runtime migration lineage. A failed process stop
preserves the private scratch path and reports the manual-cleanup target rather
than deleting a potentially live working tree.

The selected database timestamp is the oldest cross-checked value from its key,
metadata created epoch, and S3 LastModified. This is storage-consistency
evidence, not signed backup provenance. It fails if that conservative age is
over 3,600 seconds. The monotonic 1,800-second measurement covers exact-object
download through isolated application smoke and is reported as
`technicalRestoreSeconds`; it is not a customer RTO claim. Store the resulting
mode-0600 JSON evidence in the approved private evidence system and remove the
temporary age identity from the drill host.

The drill is not a production restore command. A real restore still requires
incident command, explicit production authorization, an exact recovery-point
selection, current migration compatibility review, service stop, and the
existing fail-closed restore/release procedure.

Until site provisioning, private provider-control evidence, a first retained
drill, and a separately measured incident/customer recovery window exist, this
section is an implementation procedure only; quarterly RPO/RTO readiness
remains MANUAL_REQUIRED.
