Nexus application disaster recovery
===================================

Status and boundary
-------------------

Quarterly restore-drill readiness is MANUAL_REQUIRED. The repository contains
a fail-closed isolated boot/smoke/stop implementation, but repository presence
is not site readiness. `restore-readiness.json` is the machine-readable status.
Do not claim quarterly restore readiness until the assets, dedicated nologin
account, provider controls, and off-host age identity are provisioned and one
complete drill has produced retained evidence.

These are installation templates. Adding them to the repository does not
install a timer, create a bucket, upload data, delete backups, restore data, or
change production. Installation and every restore remain owner-authorized
operations. The restore drill is intentionally incapable of applying anything
to the production path.

The application DR boundary is separate from SonarQube backup. It covers:

1. the live Nexus SQLite database through SQLite's online backup API;
2. each local v*.tar.gz exact-release rollback bundle; and
3. a quarterly isolated release-plus-database boot and smoke proof.

Object-store preparation
------------------------

Create a private object-store bucket reachable only over HTTPS. For
`aws-s3:versioned-s3`, grant the ServerDominguez backup identity only
exact-prefix-scoped `s3:ListBucket` and `s3:ListBucketVersions`, object
Get/Head/Put, and the narrowly scoped
GetObjectRetention/PutObjectRetention actions required to apply the final
COMPLIANCE deadline during each initial upload. The backup identity has no
`DeleteObject`, `DeleteObjectVersion`, legal-hold, bucket-policy, lifecycle,
versioning, or Object Lock mutation path. AWS cleanup belongs exclusively to
reviewed S3 Lifecycle rules. The bucket also denies governed object writes from
every principal except the exact backup role, even if another same-account
identity policy is accidentally broad. The approved R2 variance instead
retains its existing prefix-scoped ListBucket and object
Get/Head/Put/Delete permissions because R2 has no S3 versions or Object Lock
equivalence. Deny plaintext transport in either mode.

For AWS S3, provision `aws-s3-stack.yaml` through a reviewed CloudFormation
change set. The template retains the bucket on stack deletion, enables
versioning and Object Lock without applying a default lock to the shorter-lived
database tiers, enables default server-side encryption and public-access
blocking, denies plaintext transport and unversioned deletion, and grants only
the configured prefix. `PrincipalProvisioningMode=EXTERNAL` preserves the
existing contract for owner-supplied roles. For ServerDominguez, select
`IAM_ROLES_ANYWHERE`: the same atomic stack creates distinct least-privilege
backup and restore roles, one-role profiles, a certificate-bundle trust anchor,
and its CloudFormation-owned CRL. Supply only the public certificate for an
owner-controlled private CA and the 74 exact CRL chunks generated by
`scripts/application-dr-crl-parameters.mjs`. CloudFormation limits each
parameter value to 4,096 bytes, so the helper emits 73 4,096-byte chunks and
one 992-byte chunk to cover the full 300,000-byte IAM Roles Anywhere CRL
service limit. It also emits the exact SHA-256 binding and mode-0600 generation
evidence. The template never accepts or creates a CA key, leaf key, leaf
certificate, access key, or login profile.
It does not create an IAM access key or any other long-lived AWS credential.
The writer requires bounded `PutObjectRetention` permission to attach each
object's final lock during its initial upload. A compromised writer could keep
extending objects to the tier's one-day upper bound and cause storage-cost
growth, but it still cannot shorten retention, delete versions, change legal
holds, or mutate bucket controls. Alert on unexpected retention changes and
disable the Roles Anywhere profile and trust anchor during credential response.

Before preparing every change set, validate the exact reviewed template with
both structural linting and the repository policy-as-code rules:

  cfn-lint ops/application-dr/aws-s3-stack.yaml
  cfn-guard validate --rules ops/application-dr/aws-s3-stack.guard \
    --data ops/application-dr/aws-s3-stack.yaml --type CFNTemplate \
    --show-summary all

Both commands must pass. Guard protects the retained Object Lock bucket and
policy, versioning, AES256 encryption, complete public-access blocking,
bucket-owner-enforced ownership, the exact two-role/two-profile managed
identity plane, absence of IAM users/access keys, and disabled-first lifecycle.
The template defaults both activation controls to DISABLED and rejects a
pre-staged lifecycle receipt. CloudFormation rules cannot observe an earlier
stack state, so every later DISABLED-to-ENABLED update is enforced by the
reviewed external activation controller described below.

Generate the initial CRL parameters from a private mode-0700 working directory:

  node scripts/application-dr-crl-parameters.mjs generate \
    --operation bootstrap \
    --issuer-cn nexus-application-dr-ca \
    --ca-certificate /absolute/reviewed/ca-certificate.pem \
    --crl /absolute/reviewed/current.crl.pem \
    --parameters-out /absolute/private/crl-parameters.json \
    --evidence-out /absolute/private/crl-parameters-evidence.json

The first managed-mode change set must use
`RolesAnywhereActivation=DISABLED`, `LifecycleActivation=DISABLED`,
`LifecycleBootstrapReceiptSha256=''`, and `CAPABILITY_IAM`, supply all 74
generated chunk values plus `CertificateRevocationListSha256`, and be reviewed
before execution. Never use
`UsePreviousValue` for a CRL chunk: every change set supplies one complete,
byte-identical generated parameter set. Bind the stack's exact bucket, prefix,
role, trust-anchor, CRL, and profile outputs into the root-only runtime
configuration. Never infer a generated IAM role path/name or CRL identifier
from a label.

The template does not publish or accept a claimed prior-stack identifier.
CloudFormation template rules cannot prove historical state, so a direct
enabled-first CREATE is procedurally forbidden and is not activation evidence.
The owner must review and execute the initial CREATE with both controls
disabled, retain its exact stack ARN and completed live-state verification,
enable CloudFormation termination protection before any activation review,
and use that existing stack only through the external activation controller.
For an existing disabled stack created from an earlier template, install the
static `RolesAnywhereActivationRollbackAlarm` in a separate disabled-state
change set first. That preactivation change set must not enable any identity or
lifecycle resource. Wait until the alarm naturally reaches `ALARM` with no
metric publisher. The later exact enable change set must not add or modify the
alarm; its resource changes remain limited to the four managed Roles Anywhere
controls.

The disabled-lifecycle exception is not the ordinary storage-control contract. It
is a single-use bootstrap for a fresh namespace whose lifecycle has never been
enabled and whose complete object, version, and delete-marker inventories are
all zero. A completed Roles Anywhere activation update is allowed only while
that lifecycle history remains false and the receipt parameter remains empty.
Record those observations in the strict
`nexus.application-dr-storage-controls.bootstrap.v1` evidence shape below. Do
not relabel an existing v2 observation or a legacy prefix as bootstrap evidence.

After the first stack operation, run the helper's read-only `verify` command
with `--expected-enabled false`. It must bind the exact account, region, trust
anchor, exact backup and restore profile ARNs/IDs, CRL ID/name, returned CRL
bytes, digest tag, CA certificate, and generation evidence in a new mode-0600
live receipt. Supply `--backup-profile-arn` and `--restore-profile-arn` from
the exact CloudFormation outputs; the verifier requires the trust anchor, both
profiles, and CRL to all equal `--expected-enabled`. Then prepare one UPDATE
change set that re-supplies every explicit parameter and the same 74 chunks
and digest while changing only `RolesAnywhereActivation=ENABLED`. Capture the
complete `describe-change-set --include-property-values` JSON as a new
root-owned mode-0600 file. It must retain the current tags, notification ARNs,
and execution-role identity. It must attach exactly the stack output
`RolesAnywhereActivationRollbackAlarmArn` as an
`AWS::CloudWatch::Alarm` rollback trigger with
`MonitoringTimeInMinutes=30`; it must use standard
rollback-enabled deployment and must not import resources, revert drift, use
nested stacks, or add any resource change outside the four managed Roles
Anywhere controls.

CloudFormation saves rollback-trigger configuration on the stack, inherits a
saved list when a later update omits it, replaces it when a new list is
supplied, and clears it only when the request supplies an explicit empty list.
Create the ENABLE change set with the exact stack output, not a hand-derived
alarm name:

  aws cloudformation create-change-set \
    --stack-name '<exact stack ARN>' \
    --change-set-name '<owner-reviewed unique name>' \
    --change-set-type UPDATE \
    --capabilities CAPABILITY_IAM \
    --parameters file:///absolute/private/complete-explicit-parameters.json \
    --template-body file://ops/application-dr/aws-s3-stack.yaml \
    --rollback-configuration \
      '{"RollbackTriggers":[{"Arn":"<exact RolesAnywhereActivationRollbackAlarmArn output>","Type":"AWS::CloudWatch::Alarm"}],"MonitoringTimeInMinutes":30}'

Derive the controller's current-parameter digest from a fresh private AWS
response rather than reproducing JSON normalization by hand:

  umask 077
  aws cloudformation describe-stacks \
    --stack-name '<exact stack ARN>' \
    --output json > /absolute/private/current-stack.json
  /usr/local/libexec/nexus-application-dr/application-dr-cloudformation-parameter-digest.py \
    --describe-stacks-json /absolute/private/current-stack.json \
    --expected-owner-uid 0 \
    --trust-boundary /absolute/private

The helper emits only the canonical digest, parameter count, and hashed stack
identity; it never emits parameter values.

Some AWS CLI/API versions omit `RoleARN` from `describe-change-set`. Therefore
the authorization that creates the change set must deny `iam:PassRole`
entirely when the current stack has no execution role, or allow it only for
the exact current stack execution-role ARN. The create request must omit
`--role-arn` when the current stack has none. The controller compares RoleARN
when AWS returns it and always compares the final stack controls, but that
post-update check is detection, not a substitute for this pre-execution IAM
boundary.

Inspection never executes the change set. It verifies the current stack and
live controls twice, compares the complete live change-set JSON and both
current/proposed template bytes with the reviewed digests, requires termination
protection and an idle `ALARM`, enforces the exact parameter, rollback trigger,
alarm, executable, argument, and resource transition, and writes one immutable
mode-0600 review receipt. The two argument files are exact JSON argv arrays for
the read-only enabled-state CRL verifier and bounded positive/revoked probe;
their output paths must equal the corresponding controller evidence paths.
After the owner reviews that receipt and its SHA-256, repeat the exact command
with `--operation execute` instead of `inspect` and add:

  --review-receipt-sha256 <owner-approved review receipt SHA-256> \
  --evidence-out /var/lib/nexus-application-dr/evidence/roles-anywhere-activation.v1.json \
  --execute-reviewed-change-set

Execution re-runs every inspection check, requires unchanged reviewed files and
receipt bytes, writes and fsyncs a root-private journal before publishing the
first metric, primes the exact alarm to `OK`, re-observes the exact predecessor,
change set, proposed template, and owner-approved receipt, then checkpoints
`execution-attempted` before executing only the exact change-set ARN. It keeps
one sequential lease alive only while the reviewed transition continues to
pass. After the identity resources are enabled it
first runs the reviewed read-only CRL verifier to create the fresh enabled-state
evidence consumed by the positive/revoked probe. It then verifies the exact
stack parameters, resource identities, stack-level controls, trust anchor,
byte-identical and digest-tagged CRL, both profiles, disabled S3 lifecycle,
positive credential path, and revoked credential denial. These steps are
sequential; there is no external evidence producer or parallel heartbeat. It
continues those checks through
CloudFormation's 30-minute monitoring period and publishes pass evidence only
after `UPDATE_COMPLETE`.

If the controller, host, or short-lived AWS credentials disappear, no
background publisher remains. The exact alarm is 24 consecutive 30-second
missing-data-breaching periods, so the stack-scoped lease expires in
approximately 12 minutes and CloudFormation owns rollback. This longer bound
applies only to disabled identity provisioning: the application release is not
cut over and both backup and health timers remain disabled. It is deliberately
distinct from the production promotion recovery objective of 120 seconds. The
lease contract permits at most seven validated AWS calls of at most 30 seconds
each between renewals, a 210-second AWS chunk. Each external verifier has a
300-second outer bound. The larger bounded chunk therefore leaves at least 420
seconds in the 720-second alarm window, including a 120-second required safety
margin. A failed, timed-out, or structurally invalid observation never renews
the lease. No concurrent publisher, service, or timer may emit
`Nexus/ApplicationDR ActivationLease` for the stack.

After interruption, never repeat `execute`. Resume the exact journal:

  sudo /usr/local/libexec/nexus-application-dr/application-dr-cloudformation-activate.py \
    <the exact reviewed execute arguments, without --execute-reviewed-change-set> \
    --operation recover-or-finalize

Recovery never starts or repeats the change set. It re-inspects the exact
journal-bound stack and change set, then either proves execution never began
and records a safe abort, resumes exact verification of the accepted operation,
or waits without renewing an `ALARM` lease until CloudFormation restores the
reviewed predecessor. An `execution-attempted` checkpoint whose acceptance is
still ambiguous remains fail-closed for another recovery inspection. Use a
separate owner-approved,
short-lived activation profile. Never widen or reuse the backup/restore role
for CloudFormation authority. If the execution host is not ServerDominguez,
use the exact reviewed controller from the same protected source with explicit
owner UID and trust-boundary pins; do not copy credentials to the server.

The positive and revoked profiles must differ only in their leaf certificate
and private-key paths. The probe binds both profiles to the exact enabled
trust anchor, backup profile, locally verified CA/CRL bytes, and a fresh
read-only live-CRL receipt. OpenSSL must prove that both leaf certificates are
otherwise valid, that each certificate matches its private key, that the
positive certificate passes CRL checking, and that the reviewed revoked
certificate fails it. The probe then sandwiches the denied revoked
credential attempt between two successful exact-role calls and verifies the
prefix-scoped list permission. It does not depend on machine-specific AWS
error wording. It hashes bounded public results into mode-0600 evidence and
never persists temporary credentials, private-key bytes or digests, account
identifiers, object keys, or raw denial text. The probe runs subprocesses with
a minimal environment that discards endpoint, proxy, CA, loader, and Python
overrides. Keep the revoked test configuration and all private-key custody
outside version control; remove the revoked test private key from
ServerDominguez after retaining the probe evidence.

The final `If-None-Match: *` bucket policy is intentionally incompatible with
the legacy mutable-tier writer. For the current empty AWS namespace, deploy the
final write-once stack directly with both activation parameters disabled. If a
future migration targets any nonempty legacy prefix, do not enable the final
write policy or lifecycle in place. Immediately after a confirmed recovery
point, stop the timer, inventory every exact legacy VersionId, keep lifecycle
disabled for that namespace, preinstall the write-once client, and bind a fresh
versioned prefix through a reviewed change set. Run and verify one observed
locked backup in the fresh prefix before enabling its lifecycle. Keep the
legacy prefix and its lifecycle unchanged until the fresh namespace proves 24

required exact-release escrow. Retire the legacy namespace only through a
separate owner-reviewed change set and retained inventory. Never apply the
conditional-write deny before its compatible client is installed.

ServerDominguez is not EC2 and has no instance profile. The default AWS design
is IAM Roles Anywhere with 900-second credentials, a dedicated backup role, and
a root-only pinned `aws_signing_helper` credential process. Managed mode binds
each role trust to the exact account, trust-anchor source ARN, private-CA issuer
CN, and distinct leaf subject CN. Explicit profile mappings expose only issuer
CN and subject CN; each profile names one role and repeats the exact bucket and
prefix permission ceiling as a session policy. Do not put an IAM-user access
key in `backup.env`. Use a separate leaf certificate and read-only restore role
for the isolated drill; it may list exact-prefix versions and read exact object
versions/retention, but may not write or delete. The backup selects
`nexus-application-dr-backup`; the restore drill overrides it with the
`NEXUS_DR_RESTORE_AWS_PROFILE=nexus-application-dr-restore` profile from the
same root-only AWS config and validates that credential-process boundary again
before any download. Bind the exact CloudFormation outputs in
`NEXUS_DR_AWS_BACKUP_ROLE_ARN` and `NEXUS_DR_AWS_RESTORE_ROLE_ARN`; the runtime
rejects a selected profile whose credential process names another role and
rejects equal writer/restore roles.

Install `aws-config.example` as `/etc/nexus-application-dr/aws-config`,
root:root mode 0600, after replacing every placeholder. Install the reviewed
Linux x86-64 `aws_signing_helper` as the exact absolute path declared in
`backup.env`, root-owned and not group/world writable, and bind its reviewed
SHA-256 in `NEXUS_DR_AWS_SIGNING_HELPER_SHA256`. Keep
`AWS_SHARED_CREDENTIALS_FILE=/dev/null`, `AWS_EC2_METADATA_DISABLED=true`, and
the dedicated `AWS_PROFILE`; the backup rejects long-lived access-key,
web-identity, container-credential, or alternate shared-credential
environment paths in AWS S3 mode. Every helper, config, certificate, and
private-key path and parent must be canonical, root-owned, and not
group/world writable. The private key must be mode 0400 or 0600; the
certificate may be root-readable mode 0400, 0444, 0600, or 0644. HSM,
PKCS#11, TPM, or device-backed paths are not accepted by this implementation
until an owner-approved custody design and corresponding validator change are
reviewed together.

The backup unit has `PrivateDevices=true`. Before unattended Roles Anywhere is
enabled, the owner must approve the certificate issuance/rotation/revocation,
private-key and PIN custody, and either a narrowly reviewed systemd device
allowance, an isolated signing-helper service/socket, or an explicitly
accepted protected software-key fallback. Secrets Manager cannot bootstrap
this private key because AWS credentials are needed to retrieve it. Until that
credential and unattended-unlock design is approved and tested, do not enable
the backup timer.

IAM Roles Anywhere does not consult OCSP or CRL distribution points. Rotate the
CloudFormation-owned CRL through three sequential, owner-reviewed checkpoints:
(1) set `RolesAnywhereActivation=DISABLED`; (2) generate a complete
`--operation rotate` parameter set using the exact current live CRL as
`--prior-crl`, update the stack, and verify the new CRL while it remains
disabled; (3) re-supply the same complete chunks and digest while enabling the
identity plane, then verify the live enabled state. Rotation requires an
increasing CRL number and last-update time and a superset of every previously
revoked serial, so rollback cannot silently un-revoke a certificate. The
helper never calls ImportCrl, UpdateCrl, EnableCrl, DisableCrl, or DeleteCrl;
CloudFormation remains the sole normal lifecycle owner.

For an emergency, first disable both profiles and the trust anchor through the
reviewed activation change set; then update the CRL and revoke or replace the
affected leaf certificate. A break-glass direct CRL API update requires fresh
owner authorization, may occur only while the identity plane and backup timer
remain disabled, and must be reconciled byte-for-byte into CloudFormation
before re-enablement. Issued 900-second STS sessions are not retroactively
terminated by disabling the trust anchor or profiles. CloudTrail evidence must
show the expected subject and source identity for both the positive credential
test and the revoked-certificate rejection.

The default control mode is `aws-s3:versioned-s3`: bucket versioning must be
enabled and every governed upload must be conditional, checksummed, and
COMPLIANCE locked. Database minimum lock floors are 2 days hourly, 8 days
daily, 35 days weekly, and 190 days monthly; release objects have at least 90
days. S3 Lifecycle expiry follows those deadlines and is asynchronous, so
observed counts may exceed 24/7/4/6 and 90 days.

Cloudflare R2 does not satisfy the versioned-S3 control. It may be used only as
the explicit `cloudflare-r2:r2-approved-variance`: retain owner approval for
the missing versioning control and enable a Cloudflare bucket lock on exactly
`<NEXUS_DR_S3_PREFIX>/releases/` for at least 90 days. The database count-based
tiers remain outside that lock. Never label R2 versioned or silently select the
variance from the endpoint.

Record the observed provider controls in
`/etc/nexus-application-dr/storage-control-evidence.json`, root:root mode 0600.

Install in an approved maintenance window
-----------------------------------------

1. Install age, AWS CLI v2, the release-locked root-owned Node runtime, Python
   3.12, curl, GNU coreutils, util-linux, and iproute2 from the approved host
   package source. The backup and restore commands fail if a required tool is
   absent.
2. From the same root-owned, non-group/world-writable reviewed source tree used
   by the promotion bootstrap, run:

     sudo <reviewed-root>/scripts/application-dr-systemd-install.sh \
       <reviewed-root>

   The transactional installer validates `install-layout.tsv`, installs every
   exact asset, including the two-step CloudFormation activation controller,
   with its declared root owner/mode, creates the private
   `nexus-drill` nologin account without supplementary groups, and preserves
   the matched timers' prior enabled/active state. On the first upgrade from
   the backup-only layout, it gives the new health timer the already-approved
   backup timer state; a disabled backup remains disabled. It rolls back that
   timer adoption together with partial file and account changes on failure.
   Do not copy these files manually or run the
   installer from an application-user-writable checkout. The promotion
   bootstrap invokes this same installer first so its worker and DR interface
   cannot drift. A host interruption leaves the durable root-only
   `/var/lib/nexus-application-dr/install-in-progress.v1` marker in place.
   Before any account or installed-target mutation, the installer also retains
   its exact mode-0600 recovery program, source/predecessor digests, exact
   systemd enabled/active states, drill-account creation obligation, and
   per-target commit checkpoints in root-private state. In-process failure and
   reboot recovery both invoke that same retained verifier. It restores and
   proves every prior timer/recovery-service state and verifies removal of any
   transaction-created user and private group before it may remove the
   journal. A failed disable, stop, user deletion, or group deletion retains
   the journal and leaves both timers stopped. It commits
   and enables `nexus-application-dr-install-recovery.service` before any
   application asset. Once that enrollment checkpoint is durable, a reboot
   rolls an interrupted transaction back before either DR timer or service may
   start. Before enrollment, the durable journal already blocks backup writes;
   the read-only health check verifies the marker with that exact
   journal-bound recovery program and reports `installing` for at most 15
   minutes. A malformed, unrecoverable, future-dated, or older marker fails
   closed and alerts rather than masking stale recovery evidence.
   Recovery preflights the complete exact target set before changing any
   target; an unknown, missing, or digest-mismatched target leaves the journal
   and both timers fail closed for owner review. The backup unit and direct
   backup command also refuse to run while the marker exists.
   Rerunning the same reviewed installer invokes only the transaction-bound
   retained recovery program, emits
   `install-recovery-receipt.v2.json`, and stops for review; run the installer
   once more only after that rolled-back receipt is accepted. A successful
   install verifies every installed digest and mode, removes and fsyncs the
   journal as its commit point, and only then emits
   `install-receipt.v2.json`; a pass receipt can never authorize a transaction
   that remains recoverable.
3. Create `/etc/nexus-application-dr/backup.env` from `backup.env.example`,
   `/etc/nexus-application-dr/aws-config` from `aws-config.example`, and the
   provider control evidence described above, all root:root mode 0600. Install
   the reviewed helper at the configured immutable path and record its exact
   SHA-256. Use only the owner-approved short-lived credential process
   described above; never commit credentials, private provider evidence, the
   signing key, its PIN, or the age private identity.
4. Confirm the configured database is a canonical, application-user-owned
   regular file with mode 0600, 0640, or 0660. Confirm the rollback directory is
   canonical, application-user-owned mode 0700 and its v*.tar.gz files are mode
   0600. Remediate permissions deliberately; do not relax script validation.
5. Keep `nexus-application-dr-backup.timer` disabled and run:

     sudo systemd-tmpfiles --create
     sudo /usr/local/libexec/nexus-application-dr/application-dr-backup.sh \
       --config /etc/nexus-application-dr/backup.env --verify-config

   Ordinary AWS evidence must return
   `lifecyclePhase=enabled bootstrapReceipt=not-applicable`. A fresh AWS
   namespace instead returns
   `lifecyclePhase=disabled-bootstrap bootstrapReceipt=absent`; in that case
   follow the single-use owner-run bootstrap sequence above while the timer
   remains disabled. Do not pass `--bootstrap-first-backup` to
   `--verify-config`, a systemd unit, or a timer.
6. For a fresh namespace, owner-review the completed receipt and its emitted
   SHA-256, use the controller's lifecycle inspect/approval/execute sequence
   for the CloudFormation update that sets
   `LifecycleActivation=ENABLED` and the exact
   `LifecycleBootstrapReceiptSha256`, install new ordinary enabled v2 evidence,
   and rerun `--verify-config`. Require the exact enabled/not-applicable state.
7. Only after step 6 (or an already-enabled ordinary verification in step 5)
   succeeds, run:

     sudo systemctl daemon-reload
     sudo systemctl enable --now \
       nexus-application-dr-backup.timer \
       nexus-application-dr-health.timer

8. Run one owner-observed ordinary service invocation, inspect its journal, and
   verify the four database objects and every current release rollback object
   through a read-only bucket listing. The backup writes only a bounded
   root-owned `last-success.v1.json`; the five-minute health timer fails if
   that evidence is invalid or older than one hour while no backup is in
   progress. Both services invoke the installed `OnFailure` hook, which emits
   an `auth.alert` journal/syslog record and maintains redacted mode-0600 alert
   evidence below `/var/lib/nexus-application-dr/alerts/`. Confirm both timer
   states match. The health unit deliberately has no backup-config existence
   condition, so deleting or corrupting configuration cannot silence stale
   recovery-point monitoring. Deliberately fault one test invocation, observe
   its alert, then require a successful backup plus health check to mark the
   alert resolved before declaring monitoring ready.

Backup and retention behavior
-----------------------------

The hourly service is a sequential one-shot task. A non-blocking lock prevents
overlap; a second invocation fails visibly. The snapshot is taken near minute
05 of every UTC hour and the unit has a 50-minute deadline. Missing or delayed
runs are failures, not silently accepted RPO exceptions.

The scheduled unit does not start while the root promotion journal has an
active transaction. Promotion itself creates exact encrypted database and
recovery-runtime escrow points before mutation and after the soak, so this
prevents a redundant timer invocation from racing the sequential release
without weakening its DR checks. The five-minute health check remains active
and alerts if an interrupted release leaves both the transaction and the
hourly recovery point stale.

The service creates and integrity-checks a transactionally consistent SQLite
snapshot while Nexus remains online. It encrypts the snapshot in a root-only
temporary directory, deletes plaintext, uploads the same encrypted point to
four governed tiers, and verifies exact remote VersionId, checksum, size,
metadata, calendar identity, COMPLIANCE mode, and deadline:

  database/hourly   unique invocation key, >=2-day lock, 3-day lifecycle
  database/daily    first point per UTC date, >=8-day lock, 9-day lifecycle
  database/weekly   first point per ISO week, >=35-day lock, 36-day lifecycle
  database/monthly  first point per UTC month, >=190-day lock, 191-day lifecycle

The plan's `24 hourly, 7 daily, 4 weekly, 6 monthly` contract is a minimum
consecutive recovery-point floor, not an exact remote object count. Exact
count pruning is incompatible with COMPLIANCE Object Lock and with
asynchronous S3 Lifecycle expiration. The lock windows cover the worst age of
the oldest selected calendar point plus scheduling slack: one additional day
for the hourly and daily tiers, one additional ISO week for weekly, and enough
day variance to cover six unequal calendar months for monthly. Each lifecycle
threshold is one further day beyond the corresponding lock floor, so Lifecycle
does not make an object eligible while its governed minimum lock can still be
active. S3 may retain additional objects after eligibility. Readiness therefore
selects exactly the newest consecutive 24/7/4/6 period identities from the
complete version inventory, verifies each exact VersionId, and reports any
additional visible points without treating them as a policy violation.

AWS sends `If-None-Match: *` for every governed object. A collision on the
unique hourly key is a hard failure. A daily, weekly, or monthly 412 is
idempotent only when a checksum-enabled HEAD proves the existing first point
belongs to that calendar period and still satisfies every metadata, VersionId,
COMPLIANCE, and deadline invariant. A 409 receives one bounded retry; all
other errors fail.

For `aws-s3:versioned-s3`, the service explicitly exhausts direct 1,000-entry
`ListObjectVersions` pages with paired key/version markers; AWS CLI
auto-pagination is disabled. The root-owned helper validates the complete
`NexusApplicationDrVersionListingV1` envelope and emits read-only
`NexusApplicationDrRetentionEvidenceV1`. It reports configured policy and the
observed consecutive 24-hour/7-date/4-ISO-week/6-month floor separately because
a new namespace needs time to mature. Every selected exact VersionId is
checksum-HEADed and its metadata, calendar identity, COMPLIANCE mode, and tier
deadline are verified. First maturity creates a root-owned monotonic seal; a
later regression fails instead of returning to warming. It never emits or
executes deletion instructions. Missing current-period points are failures; an
immature historical floor is visible but does not fabricate readiness. S3
Lifecycle is the only AWS cleanup actor, and its eventual timing means retained
counts are minimum floors rather than exact counts.

The approved R2 variance deliberately keeps the visible-object
ListObjectsV2/DeleteObject algorithm because R2 cannot provide S3 version
identities. Do not reuse that variance path for AWS.

The same invocation scans every current v*.tar.gz bundle in the existing local
rollback directory, verifies ownership/mode and tar readability, encrypts each
previously unseen exact digest, and uploads it under releases/. Cloud escrow is
written conditionally under COMPLIANCE retention and kept for at least 90 days.
Lifecycle expiration is configured after that lock window; the backup
credential never prunes AWS release versions.

Promotion also creates two transaction-bound candidate recovery objects:
`+escrow-<transaction-id>+phase-pre-mutation...` before PM2/data mutation and
`+escrow-<transaction-id>+phase-post-soak...` after candidate availability and
the 60-second soak. They bind the same runtime, artifact, installed-tree,
recovery-runtime, release-manifest, and staging-attestation identities, but
must use distinct object keys and newly encrypted ciphertext. The post-soak
phase also writes the predecessor rollback bundle under a distinct
`+rollback-escrow-<transaction-id>+phase-post-soak` key, so an older timer upload
cannot shorten the promotion's required 90-day recovery window. Governed AWS
uploads use one-day lock headroom and can extend the same exact COMPLIANCE
version after a delayed checkpoint resume without weakening that confirmation
floor. Each phase records `escrowId`, `escrowPhase`, plaintext/encrypted SHA-256,
encrypted byte
size, `confirmedAt`, `retainUntil`, and the exact AWS `objectVersionId`. AWS
requires `retainUntil` to be at least 90 days after `confirmedAt`. R2 emits null
for unavailable deadline/version fields and explicitly records
`retentionVariance: r2-approved-variance` plus
`approvedUnversionedVariance: true`.

Each exact key/version pair is re-HEADed and re-downloaded by exact AWS
VersionId. The pre-mutation recovery object is accompanied by a fresh unique
hourly database encrypted identity/version before cutover. The post-soak object
is accompanied by another unique hourly database identity/version, and
candidate readiness is recorded both before and after those post-soak uploads.
The promotion transaction also requires positive off-host confirmation for its
predecessor rollback-bundle digest before that bundle is eligible for local
count pruning. The existing local policy keeps the latest ten bundles, while
the hourly service reconciles and re-verifies the whole retained set. A failed
escrow remains visible and the unconfirmed bundle must stay local; operators
must never prune it merely to satisfy the count.

Quarterly isolated restore drill
--------------------------------

Prefer a separate recovery host. If that is impossible, run only in an
owner-approved low-load window on ServerDominguez. The supported root-owned
harness uses private network, mount, and PID namespaces; shadows host home and
temporary paths; remounts the host root read-only; drops every capability; and
runs the restored backend as the dedicated nologin account. It refuses a live
path, a host-visible listener, inherited connector credentials, provider/model
access, local authentication bypass, or an unverified process identity.

The installed harness receives one of boot, smoke, or stop plus the absolute
scratch runtime as argv[2], and these mandatory environment values:

  NEXUS_DRILL_MODE=isolated-restore
  NEXUS_DRILL_ROOT=<private scratch exact-release tree>
  NEXUS_DRILL_DATABASE_PATH=<scratch tree>/data/bot.db
  NEXUS_DRILL_BASE_URL=http://127.0.0.1:<dedicated high port>
  NEXUS_DRILL_STATE_DIR=<private application DR state>
  NEXUS_DRILL_USER=<dedicated nologin user>
  NEXUS_DRILL_NODE_BIN=<root-owned release-locked Node>
  NEXUS_DRILL_PYTHON_BIN=<root-owned Python 3.12>

Before boot, the restore command verifies and installs the Node archive and
Python wheelhouse embedded in the exact release. Installation runs as the
dedicated account, with no inherited credentials, in a private network
namespace and with pip `--no-index`; it neither reuses production dependencies
nor downloads packages. The smoke proves connected restored SQLite health,
rejects an invalid bearer token, accepts only the one-use read token, checks
the exact release snapshot, and compares a representative API read with the
restored database. stop validates the exact recorded process and terminates
only its process group; it is idempotent.

Select the newest exact keys by read-only listing under database/hourly/ and
releases/. Then run, with a freshly copied root:root mode-0600 age identity:

  sudo /usr/local/libexec/nexus-application-dr/application-dr-restore-drill.sh \
    --config /etc/nexus-application-dr/backup.env \
    --database-key '<exact newest hourly key>' \
    --database-version-id '<exact retained AWS VersionId>' \
    --release-key '<exact compatible release escrow key>' \
    --release-version-id '<exact retained AWS VersionId>' \
    --identity-file /run/nexus-dr-age-identity \
    --output /var/lib/nexus-application-dr/evidence/quarterly-YYYYQn.json

For AWS, obtain both VersionIds from retained private backup evidence or an
exact read-only version listing; the drill HEADs and downloads only those
versions. Omit both version arguments for the approved R2 variance. The command
cross-binds the recovery key, original filename, and plaintext SHA-256; enforces
bounded HEAD/range-download sizes and scratch capacity; verifies encrypted and
plaintext SHA-256 values, SQLite integrity/foreign keys, hostile archive paths,
and the signed exact-runtime inventory; and runs all reconstructed dependency
code only as the dedicated nologin account in a private no-network namespace.

Before boot it permits only an exact governed migration prefix. After the
isolated processes stop, it takes a fresh SQLite online-backup snapshot so any
committed WAL state is included, repeats integrity/foreign-key validation, and
requires the exact terminal runtime migration lineage. A failed process stop
preserves the private scratch path and reports the manual-cleanup target rather
than deleting a potentially live working tree.

The selected database timestamp is the oldest cross-checked value from its key,
metadata created epoch, and S3 LastModified. This is storage-consistency
evidence, not signed backup provenance. It fails if that conservative age is
over 3,600 seconds. The monotonic 1,800-second measurement covers exact-object
download through isolated application smoke and is reported as
`technicalRestoreSeconds`; it is not a customer RTO claim. Store the resulting
mode-0600 JSON evidence in the approved private evidence system and remove the
temporary age identity from the drill host.

The drill is not a production restore command. A real restore still requires
incident command, explicit production authorization, an exact recovery-point
selection, current migration compatibility review, service stop, and the
existing fail-closed restore/release procedure.

Until site provisioning, private provider-control evidence, a first retained
drill, and a separately measured incident/customer recovery window exist, this
section is an implementation procedure only; quarterly RPO/RTO readiness
remains MANUAL_REQUIRED.
