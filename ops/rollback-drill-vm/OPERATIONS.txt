Nexus rollback-drill KVM environment
====================================

Purpose
-------

This environment is an isolated Ubuntu 24.04/x86-64 staging host for the three
required promotion fault drills. It is not a second release lane and it cannot
authorize production. Repository presence does not install packages, download
an image, start a guest, sign evidence, or weaken the normal staging gate.

First-drill staging boundary
----------------------------

Normal release:staging requires a current signed rollback drill, so it cannot
be used to manufacture the first drill's prerequisite. Protected first-drill
signing emits ordinary nexus.release-manifest.v2 and
nexus.staging-attestation.v1 inner envelopes signed by a dedicated drill-only
Ed25519 key. A separate signed nexus.rollback-drill-staging-bundle.v1 record
binds their raw digests and carries promotionAllowed=false, but that outer
record is never embedded in promotion.

Set releaseEvidence.releaseManifest and releaseEvidence.stagingAttestation in
the KVM input spec to the two inner files, and set
keys.releaseEvidencePublicKey to the reviewed drill public key. The generator
verifies both ordinary signatures and their exact runtime/artifact/installed/
recovery bindings before it creates a plan or promotion requests. Do not use
the production release public key: production intentionally rejects the drill
signatures.

That wrapper does not install or activate the environment. The reviewed
release:drill-staging adapter supports only the exact promotion-control v2
digest and /home/dominguez/telegram-hub-bot-staging base. Dry-run remains local
and non-promotable. Non-dry execution requires the literal
--acknowledge-first-drill-bootstrap flag, a clean checkout at the exact signed
runtime SHA, and the separately root-installed legacy staging broker. Do not
route it into the v3 /srv staging branch and do not handcraft its staging
request.

Install the broker only from the same root-owned, SHA-bound protected-main
archive described below:

  sudo /var/lib/nexus-release-bootstrap/<sha>/source/scripts/remote-rollback-drill-legacy-staging-install.sh \
    install \
    /var/lib/nexus-release-bootstrap/<sha>/source \
    <40-hex-protected-main-sha> \
    /var/lib/nexus-release-bootstrap/<sha>/source.tar.gz \
    <64-hex-root-side-archive-sha256>

The installer validates the Git PAX commit and every privileged member before
installing its root broker, tools, systemd transaction/recovery units,
fail-closed PM2 dependency drop-ins, and NOSETENV allowlisted sudoers commands.
The application account cannot invoke broker
run or recover-all. It also verifies, but does not replace, the
application-DR-owned mode-0644 SQLite helper at
/usr/local/libexec/nexus-application-dr/application-dr-sqlite.py against the
reviewed source/archive and SHA-256
e1f1a92d4dc49bd6fe6c1d8c1a3573ec2db61f6374a1831b2765a5541943708d.
The root worker holds the ordinary-promotion and
release/Sonar locks, performs the network-independent dependency installation
and candidate preflight before arming the outage, fsyncs predecessor and outage
state before changing either of the two staging PM2 names, root-pins and seals
both runtime identities, stops only those
allowlisted apps, and refuses selector mutation until no database/WAL/SHM
handle remains and a verified stopped-state SQLite recovery point is fsynced
into the root journal. Database and recovery-point inputs above 2 GiB fail
closed. Only the backup schema, digest, size, original uid/gid/mode, and
creation time enter the journal; evidence exposes only digest and size. Failure
or reboot keeps the apps stopped, rejects missing/corrupt backup bytes, removes
WAL/SHM sidecars, recreates a deleted/truncated database with its journaled
metadata, atomically restores the shared database, restores the exact
root-pinned predecessor selector, and re-attests predecessor readiness before
reporting recovery. Both PM2 units require successful boot recovery and a
final no-unfinished-journal guard. The exact-SHA PM2 identity and authenticated
readiness probe run inside the root transaction before terminal completion and
serve as the required legacy drill smoke. The Mac only submits and polls the
transaction, so closing SSH does not cancel the root one-shot.

Do not retire this exact control-v2 adapter while any transaction is active.
Run `sudo /usr/local/sbin/nexus-rollback-drill-legacy-staging-broker
assert-terminal-retirement-ready`; its success still requires the
`nexus.release-layout-fault-drill.v1` successor integration to be installed
before adapter removal.

Before any live drill, install the reviewed promotion bridge that verifies
both release-evidence signatures with its root-installed production key before
the first application-runtime mode/ownership mutation. Current-source request
validation alone does not guard an older installed bridge.

The protected bundle still authorizes only the isolated first-drill input. Its
drillBootstrap field and canonical digest are rejected by the ordinary staging
validator, and both inner signatures remain invalid under the production key.
The three real, strictly sequential outcomes and
execution receipt remain required before the existing protected
nexus.rollback-drill.v1 freshness envelope can be requested. Staging
normalization into an ordinary production-promotable attestation is a separate
future signed action; neither this wrapper nor this operations guide performs
or implies it.

Trust boundary
--------------

1. Build an exact Git archive from protected main with the standard
   `source/` prefix and Git PAX commit comment, then copy it to
   `/var/lib/nexus-release-bootstrap/<40-hex-sha>/source.tar.gz` and extract it
   as the sibling `source/` directory. Both paths and their full ancestor
   chains must be root-owned and non-writable by group or world. Record the
   root-side archive SHA-256 after the copy. Do not run either installer from a
   deploy-user-writable checkout.
2. Copy only a dedicated lab SSH public key into the same root-owned bootstrap
   directory. Never copy a production SSH key, owner promotion private key,
   production host key, application .env, database, logs, or provider data.
3. Install the reviewed assets:

     sudo /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-vm-systemd-install.sh \
       /var/lib/nexus-release-bootstrap/<sha>/source \
       <40-hex-protected-main-sha> \
       /var/lib/nexus-release-bootstrap/<sha>/source.tar.gz \
       <64-hex-root-side-archive-sha256>

   The installer creates the nologin nexus-drill-vm account with exactly one
   supplemental group, kvm. It transactionally installs the root helpers and
   static systemd template. Before any commit it proves the archive's PAX
   commit identity, compares every privileged source byte with its regular
   archive member, syntax-checks the shell/Python assets, and verifies the
   systemd templates. It does not download an image, provision a guest, or
   start a service. It enables only
   nexus-release-layout-fault-drill-recovery.service so an authenticated
   nonterminal controller journal resumes after host boot; the three guest
   templates and owner-submitted transaction template remain static and
   disabled. The guest and recovery units do not wait on `dev-kvm.device`:
   hosts that expose a valid static or container-provided KVM node may not
   publish a corresponding active systemd device unit. The guest's root
   preflight validates the live KVM device before every explicit start. The
   controller and enabled recovery service use a failing character-device
   preflight, so a late `/dev/kvm` appearance enters the existing bounded
   restart policy instead of being condition-skipped as successful. Both host
   and guest boot recovery retain bounded four-attempt retry windows.
4. From Canonical's signed SHA256SUMS, independently record the reviewed digest
   of noble-server-cloudimg-amd64.img. Then provision exactly three guests:

     sudo /usr/local/libexec/nexus-rollback-drill-vm/provision \
       --expected-image-sha256 <64-lowercase-hex> \
       --expected-image-size <owner-reviewed-bytes> \
       --ssh-public-key <root-owned-lab-public-key> \
       --ports 22991,22992,22993 \
       --acknowledge-isolated-drill-only

   Provisioning downloads only the fixed HTTPS noble/current SHA256SUMS,
   SHA256SUMS.gpg, and image names. It verifies the manifest with gpgv and
   /usr/share/keyrings/ubuntu-cloudimage-keyring.gpg, requires the signed digest
   to equal the owner-reviewed digest, validates qcow2 structure, installs an
   immutable root-owned base named by digest, and atomically publishes three
   independent overlays and cloud-init seeds. It also creates a dedicated
   root-only hypervisor Ed25519 evidence key and one guest Ed25519 evidence key
   per seed, then atomically publishes the root-owned mode-0600
   /var/lib/nexus-rollback-drill-vm/release-layout-evidence-trust.v1.json.
   That manifest binds the active provision receipt/set, QEMU and runner
   digests, guest SSH host-key digests, fixed scenario-to-guest mapping, and
   exact SHA-256 digests for the root controller, controller unit, deep
   verifier, guest executor, and guest boot-recovery unit.
   A provision journal or disagreement between that manifest and active.json
   blocks release-layout proof verification.

   When the three exact files were pre-staged under an unprivileged directory,
   add:

     --staged-source-directory <absolute-directory>

   The provisioner opens that directory and each allowlisted basename with
   no-follow file-descriptor semantics, copies the bytes into root-private
   state, detects a concurrent source change, and performs the same signature,
   owner-reviewed size/digest, and qcow2 validation after the copy. It does not
   execute a staged file and does not use the network in this mode.

Release-layout successor evidence
---------------------------------

Install the dedicated lab SSH private key corresponding to the public key used
at provision time as the root-owned, single-link, mode-0600
/etc/nexus-release/rollback-drill-vm-ssh-private.pem. The guest account has
NOSETENV sudo access only to the fixed runtime-control and fault-executor
subcommands; it cannot read a guest evidence private key or author evidence
bytes.

Create the nonce-bound plan with the protected-main
release-layout-fault-drill.mjs `prepare` command. Submit it only to the installed
root controller:

  sudo /usr/local/libexec/nexus-rollback-drill-vm/release-layout-fault-controller submit <plan.json>
  sudo /usr/local/libexec/nexus-rollback-drill-vm/release-layout-fault-controller status <plan-id>

The systemd one-shot runs failed health, guest reboot, and SSH disconnect
strictly sequentially, with at most one active guest. The controller observes
the live QEMU PID and command line, loopback-only SSH boundary, guest boot IDs,
and host monotonic recovery interval. Each root-only guest executor performs
and restores an actual selector, process, and SQLite recovery fixture, while
its boot recovery unit resumes an armed transaction after reboot. The guest
signs only after exact predecessor, database, and health restoration; the
hypervisor signs the bound isolation observation. Test-mode execution is
cryptographically ineligible for sealing.

After `status` reports `completed`, the owner-signable payload is the immutable
root-owned file below
/var/lib/nexus-rollback-drill-vm/release-layout-fault-drills/<plan-id>/.
Do not hand-author result JSON, copy evidence private keys, or use OpenSSL to
manufacture a scenario result. The deep verifier intentionally exposes no
manual `record` command.

Runtime-readiness gate
----------------------

The provisioned Noble guest is intentionally reported as
ssh_only_bootstrap_required and drillReady=false. With QEMU restrict=on it
cannot fetch the promotion toolchain, and the exact release artifact does not
contain the Node or PM2 executables. A boot proves only KVM/cloud-init/SSH.

Before any promotion drill, build and register one separately reviewed,
owner-signed offline bundle for the immutable provision set. Guest 1 is the
only Python-provenance witness; all three guests are still installed and
measured independently. The bundle contains and verifies:

- Node 22.23.1, including a root-owned mode-0755 regular
  /usr/bin/node file with link count one;
- the exact provisioned Python 3.12 package and binary identity;
- the complete PM2 6.0.14 root closure at
  /opt/nexus-release/pm2/6.0.14, the regular root-owned launcher at
  /usr/local/bin/pm2, and the digest-bound installation attestation at
  /var/lib/nexus-release-promotion/pm2-root-install.v1.json. The signed target
  independently binds the source archive, closure digest, payload digest,
  package-lock digest, and exact file count from
  closure-manifest.json; and
- the protected-main root promotion controls.

The bundle builder runs only on a trusted Ubuntu 24.04/x86-64 builder with
Node 22.23.1/npm 10.9.8. It requires a clean checkout whose HEAD and
origin/main both equal the reviewed full SHA, prepared Node release inputs,
an offline npm cache, guest 1's host-key-signed Python provenance, and a
lab-only Ed25519 owner key. The signed manifest scopes that witness to the
exact provision receipt and immutable base-image digest; it does not attest
another guest's live runtime. The builder forces npm offline, disables lifecycle
scripts, verifies the Node release signature and pinned identities, constructs
the complete PM2 lock closure, signs the canonical manifest, fsyncs the full
tree, and publishes one content-addressed directory. It performs no download.
The protected source archive must be rooted at source/. The guest copies the
same signed archive to
/var/lib/nexus-release-bootstrap/<protected-main-sha>/source.tar.gz, verifies
its digest and Git PAX commit identity, safely extracts only its source/
sibling, and invokes the five-argument v4 promotion installer from that
root-owned source tree.

The readiness measurement binds every installed v4 core promotion asset,
every application-DR install-layout asset, and all seven Ollama operational
assets by source, destination, owner, mode, size, and digest. It separately
binds generated keys, sudoers, service drop-ins, sealed production/staging
environments, the PM2 installation attestation, effective systemd unit state,
and NeedDaemonReload=false. A missing asset or an installer that provides only
a subset of that union fails closed. Before readiness is signed, the guest
invokes the installed v4 promotion control's assert-root-pm2-ready command;
failure prevents readiness publication and therefore prevents every drill.

Start guest 1's first boot, collect its Python provenance with strict host-key
checking through `nexus-rollback-drill-vm-runtime-control inspect-python`, and
keep guest 1 running while the provision-set bundle is built and registered.
Before the first readiness claim, guest 1 may perform only cloud-init, SSH
readiness, Python inspection, and bundle construction inputs; do not install
the runtime or invoke a promotion control. Set all three
runtimeBundleManifests entries in the reviewed input spec to the same
content-addressed manifest. Do not stop and restart guest 1 between provenance
collection and its readiness collector: until a readiness v2 receipt exists,
the runner accepts only the initial overlay digest.

After the three authorizations are signed and the sequence ledger is
initialized, claim and collect guest 1. The collector independently installs
and measures the shared bundle, stops guest 1, and publishes its receipt.
Only then start, claim, install, and measure guest 2, followed by guest 3.
Each authorization still binds a distinct guest, port, SSH host key, drill,
and authorization ID, and every readiness receipt binds that guest's live
Python package/binary, runtime, QEMU, and sealed overlay identities.

Pin the separately transported owner public key exactly once, then register the
signed bundle:

  sudo /usr/local/libexec/nexus-rollback-drill-vm/runtime-readiness \
    pin-owner-key <root-readable-lab-owner-public-key.pem> \
    <owner-public-key-sha256>

  sudo /usr/local/libexec/nexus-rollback-drill-vm/runtime-readiness \
    register-bundle <copied-content-addressed-bundle> \
    <bundle-manifest-sha256>

The pin command's expected SHA-256 is the digest of the exact PEM file bytes,
which also binds the signed bundle's embedded key file. Runtime
authorizations and readiness receipts use the canonical SHA-256 of that same
key's SPKI DER identity, matching the plan and readiness-sequence controls.
The collector derives both identities from the independently pinned key and
does not let the operator substitute either value.

Create three compact, sorted canonical JSON payloads with no trailing newline
using schema
`nexus.rollback-drill-vm-runtime-authorization.v1`. The signed authorization
must bind a unique 64-hex authorizationId, issuedAt, expiresAt no more than 24
hours later, the current Linux boot-ID SHA-256, matching `/proc/uptime`
issued/deadline seconds, operation `collect-runtime-readiness`, one allowlisted
drill, setId, guest, port, provision receipt digest, bundle manifest digest,
guest SSH host public-key digest, and pinned owner public-key digest. The
monotonic lifetime must equal the wall-clock lifetime exactly. Sign those exact
bytes with the same lab owner key:

  openssl pkeyutl -sign -inkey <lab-owner-private-key.pem> -rawin \
    -in <authorization.json> -out <authorization.sig>

While the currently claimed first-boot unit is still active, run:

  sudo /usr/local/libexec/nexus-rollback-drill-vm/runtime-readiness collect \
    <guest-1|guest-2|guest-3> <provision-receipt-sha256> \
    <bundle-manifest-sha256> <dedicated-lab-ssh-private-key> \
    <authorization.json> <authorization.sig> \
    <ssh-disconnect-after-pm2-stop|failed-health-check|host-reboot-during-promotion>

The collector independently verifies the pin, bundle, authorization, provision
receipt, dedicated SSH key, systemd supervisor, exact QEMU child and command
line, loopback listener, and all three orchestration locks. It installs without
network access, requests a fresh nonce-bound guest measurement, verifies the
guest host-key signature, including the exact effective guest recovery-unit
fragment, empty drop-in set, and ExecStart, journals the exact live identities,
and asks the
runner to stop QEMU while the runner retains the active and release/Sonar
locks. With the collector retaining the admission lock, it opens the qcow2 once
with O_NOFOLLOW, proves no other process holds, maps, or names that inode,
hashes the same descriptor, and verifies device, inode, size, mtime, and ctime
before and after the full hash. Only then is immutable readiness v2 published.

There is no caller-supplied guest-attestation input or static attestation
command. A collector or host restart resumes only from the root-owned journal,
reacquires the admission, active, and release/Sonar locks, and re-proves the
stopped overlay before publication. The evidence coordinator must reject a
drill while the provision receipt alone is the only readiness input. Never
enable guest egress, download through cloud-init, copy production executables
or data, or interpret SSH readiness as promotion readiness.

Sequential readiness admission
------------------------------

Use the protected-main
`scripts/rollback-drill-kvm-readiness-sequence.mjs` control before operating
the three runtime-readiness guests. It is an offline, root-only admission
ledger, not a guest runner. It snapshots the exact plan, generation manifest,
provision receipt, lab owner public key, and all three signed, guest-specific
runtime authorizations under
`/var/lib/nexus-rollback-drill-vm/readiness-sequences/<plan-sha256>`.
The fixed non-waiting control lock permits only one state transition at a time.
An existing plan ledger is never reinitialized or overwritten. Every command
rechecks the current Linux boot ID and monotonic uptime. A reboot, decreasing
uptime, or elapsed monotonic deadline fails closed and requires a newly
prepared and owner-authorized sequence.

Initialize once. The authorization directory must contain the canonical
`ssh-loss`, `failed-health`, and `guest-reboot` `.json` and `.sig` pairs:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-readiness-sequence.mjs init \
    --plan <plan.json> \
    --generation-manifest <generation-manifest.json> \
    --provision-receipt <provision-receipt.json> \
    --runtime-authorization-dir <runtime-authorization-directory> \
    --guest-owner-public-key <lab-owner-public-key.pem>

Use the request path emitted by `init` or `status`; never handcraft or copy a
request from another plan. Immediately before installing the runtime or
starting readiness collection for a guest, checkpoint the exact next request:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-readiness-sequence.mjs claim \
    --plan <plan.json> \
    --request <emitted-request.json>

Only the fixed order `ssh-loss/guest-1`, `failed-health/guest-2`, then
`guest-reboot/guest-3` is admitted. A second active guest, a later request, a
completed request replay, a stale new claim, request drift, or a request from
another plan fails closed. Claim persists before any later operator action.
Do not resume this authorization after a host reboot. Re-run preparation and
owner authorization against the new boot identity before starting a guest.

After the root collector has stopped the admitted guest and published its
readiness v2 receipt and evidence directory, complete the checkpoint:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-readiness-sequence.mjs complete \
    --plan <plan.json> \
    --request <same-emitted-request.json> \
    --readiness <runtime-readiness-v2.json> \
    --evidence-dir <collector-evidence-directory>

Completion independently verifies the owner Ed25519 authorization signature,
the guest SSHSIG host-key signature, the fresh journal challenge and handoff
nonce, and the exact plan, provision, bundle, guest, drill, port, systemd, and
live QEMU tuple. It publishes immutable receipt snapshots before advancing the
ledger. An interruption between receipt publication and state advancement is
idempotently resumed with the same command. Use `status --plan <plan.json>` at
any time for read-only recovery guidance. The third completion publishes
immutable `completed-ledger.json`, binding the exact plan, generation,
provision, ordered request/readiness digests, boot ID, monotonic window, and
terminal state digest.

This control invokes no `systemctl`, SSH, QEMU, network, evidence-coordinator,
promotion, or production action. Until a separately reviewed adapter consumes
its exact active request, a claim is only a durable operator checkpoint. The
existing systemd admission, active-guest, and release/Sonar locks remain the
physical one-QEMU enforcement boundary. Do not activate production or submit a
promotion from this readiness phase.

Input generation and signing
----------------------------

Do not handcraft plan, isolation, runtime-readiness authorization, or promotion
request schemas. The protected-main input generator derives their fixed fields,
ordered guest/drill bindings, key identities, provision identities, evidence
digests, canonical paths, 60-second soak, and short lifetimes. It never reads a
private signing key, creates a signature, starts a guest, launches promotion,
or accesses the network.

First create the owner-reviewable input-spec template in a new root-private
directory. Every `__REQUIRED__` value must be replaced with an exact
root-readable source; unresolved values fail before an output directory is
created:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-inputs.mjs template \
    --output-dir <new-root-private-template-directory>

The reviewed spec must point all three runtimeBundleManifests entries at the
same guest-1-witnessed provision-set manifest bytes. Preparation rejects
different bundle digests before creating its output.

After review, generate the plan, three canonical runtime authorization
payloads, a plan-bound isolation-observation template, and a generation
manifest:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-inputs.mjs prepare \
    --spec <completed-input-spec.json> \
    --output-dir <new-root-private-preparation-directory>

`prepare` deliberately emits no KVM owner-authorization envelope and no
promotion requests. Sign each compact runtime authorization file, whose exact
bytes contain no trailing newline, with the separately held lab owner key:

  openssl pkeyutl -sign -inkey <lab-owner-private-key.pem> -rawin \
    -in <prepared>/runtime-authorizations/<drill>.json \
    -out <prepared>/runtime-authorizations/<drill>.sig

Use those detached signatures in the three runtime-readiness collector calls.
After all three immutable readiness-v2 receipts exist, fill only the measured
fields in `isolation-observation.template.json`. In particular, bind each
receipt's raw SHA-256, record three distinct guest machine/boot identities, and
record the representative guest's live memory, disk, kernel-log, mount,
listener, PM2, synthetic-database, and zero-production-match observations.
The untouched template is intentionally invalid. Finalize it only with all
three readiness receipts, in the fixed sequential order:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-inputs.mjs finalize-isolation \
    --plan <prepared>/plan.json \
    --generation-manifest <prepared>/generation-manifest.json \
    --provision-receipt <provision-receipt.json> \
    --readiness-ledger <completed-ledger.json> \
    --observation <completed-isolation-observation.json> \
    --ssh-loss-readiness <ssh-loss-readiness-v2.json> \
    --failed-health-readiness <failed-health-readiness-v2.json> \
    --guest-reboot-readiness <guest-reboot-readiness-v2.json> \
    --output <new-isolation.json>

Only immediately before execution, generate the short-lived plan authorization
payload and three unsigned promotion requests. This avoids expiring a
30-minute request while runtime readiness is collected:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-inputs.mjs authorize \
    --spec <completed-input-spec.json> \
    --plan <prepared>/plan.json \
    --isolation <new-isolation.json> \
    --output-dir <new-root-private-authorization-directory>

Sign the exact compact plan payload with the lab owner key, then let the
generator combine and verify that detached signature. It will not publish an
envelope whose key, plan digest, endpoints, target, lifetime, or signature do
not verify:

  openssl pkeyutl -sign -inkey <lab-owner-private-key.pem> -rawin \
    -in <authorization>/plan-owner-authorization.payload.json \
    -out <authorization>/plan-owner-authorization.sig

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-inputs.mjs seal-plan-authorization \
    --plan <prepared>/plan.json \
    --isolation <new-isolation.json> \
    --payload <authorization>/plan-owner-authorization.payload.json \
    --signature <authorization>/plan-owner-authorization.sig \
    --guest-owner-public-key <lab-owner-public-key.pem> \
    --output <authorization>/plan-owner-authorization.envelope.json

Sign each generated promotion request only through the existing protected
promotion signer and publish the results under the coordinator's exact names:

  node scripts/promotion-authorization.mjs sign-request \
    --input <authorization>/promotion-requests/<drill>.request.json \
    --private-key <production-owner-private-key.pem> \
    --output <request-directory>/<drill>.envelope.json

The generated manifests always declare `strictly-sequential` execution and the
order `ssh-loss`, `failed-health`, `guest-reboot`. They do not create a second
release lane or permit concurrent guests. The owner-signed plan authorization
binds the exact isolation digest and completed readiness ledger. The
coordinator rechecks that binding and the live boot/monotonic deadline before
its first `systemctl start`; the execution receipt and final machine-evidence
bundle repeat the generation, provision, and ordered readiness digests.

Isolation
---------

- The systemd template has no Install section and stays static/inactive.
- A start is admitted only when host MemAvailable is at least 25 GiB, load-15
  is below 6, and the root preflight finds no kernel OOM evidence in the prior
  24 hours. The runner immediately repeats the memory/load check.
- systemd passes the existing root:dominguez mode-0660
  `/run/lock/nexus-release-sonar.lock` and the root:nexus-drill-vm mode-0660
  `/run/nexus-rollback-drill-vm/active.lock` as named descriptors. The latter
  lives beside a separate root:nexus-drill-vm mode-0660 admission lock under a
  root-owned, non-writable mode-0750 directory. The runner acquires admission
  before the active lock, then releases admission only after start acceptance.
  The readiness collector holds admission across QEMU stop and overlay seal.
  The runner
  validates both path/descriptor inode identities, ownership, modes, link
  count, and the exact `LISTEN_PID`/`LISTEN_FDS`/`LISTEN_FDNAMES` contract,
  then supervises QEMU while retaining both non-waiting flocks. Releases, Sonar
  operations, provisioning, and a second drill guest are therefore mutually
  exclusive without a service-user-replaceable lock inode.
- Start only one guest at a time:

    sudo systemctl start nexus-rollback-drill-vm@guest-1.service

  A shared non-waiting lock rejects a second active guest.
- Each guest has a unique qcow2 overlay, cloud-init instance id, VM UUID, and
  MAC, and newly generated Ed25519 SSH host identity. Each host identity is
  bound to exactly one guest slot and all three identities must be distinct.
  The only login is dominguez through the dedicated lab public key. Password
  and root SSH login are disabled.
- QEMU uses KVM and user-mode networking with one explicit
  127.0.0.1:<port> -> guest:22 forward. restrict=on blocks guest-initiated
  networking. There is no bridge, tap, shared filesystem, host block device,
  display, serial console, QMP socket, production mount, or public listener.
- The base and seed are root-owned and non-writable. Only the selected guest
  overlay is writable by nexus-drill-vm. Before readiness, the runner requires
  the exact initial file digest. After an immutable readiness v2 receipt, it
  accepts only that receipt's stopped-overlay current digest. Any other
  mutation requires a fresh provision set.
- The provision set binds the exact root-owned QEMU binary SHA-256, QEMU
  version output, owning Debian package, package version, and architecture.
  The runtime revalidates all five values before starting a guest.
- The guest is advertised 14,336 MiB of logical RAM so the exact production
  capacity gate can prove at least 12 GiB available inside it. Its host cgroup
  soft limit is 10 GiB, hard limit is 12 GiB, and swap limit is 512 MiB. The
  25-GiB admission floor therefore preserves at least 13 GiB on the host at
  the hard physical-memory bound, leaving the existing 12-GiB release floor
  plus a 1-GiB guard band. This logical-RAM/cgroup envelope requires measured
  cloud-init, application, and fault-drill evidence before the set can be
  considered ready; limits are never tuned automatically.

Evidence and drills
-------------------

The plan, input-spec, and provision-receipt v2 cutover is intentionally
fail-closed. Do not resume an in-flight v1 set or plan: retire it, provision a
fresh three-key v2 set, and generate new owner-signable inputs.

Use one independently sealed guest for each fault scenario. Connect with strict
host-key checking and a per-guest known_hosts file populated from the provision
receipt before the first observed boot. The cloud-init bootstrap installs only
the receipt-bound runtime helpers; the collector installs only the registered
owner-signed bundle. Use synthetic data and lab-only keys.

Run the unmodified low-level promotion control plane for:

1. coordinator/SSH loss after PM2 stop;
2. deterministic candidate-health failure;
3. guest reboot after recovery intent and predecessor stop.

Run the coordinator as root on ServerDominguez because the three SSH forwards
are loopback-only and the guest-reboot drill controls only the fixed
nexus-rollback-drill-vm@guest-N.service units:

  sudo /usr/bin/node /var/lib/nexus-release-bootstrap/<sha>/source/scripts/rollback-drill-kvm-coordinator.mjs execute \
    --plan <plan.json> \
    --authorization <guest-owner-authorization.json> \
    --isolation <isolation.json> \
    --guest-owner-public-key <guest-owner.pem> \
    --production-owner-public-key <production-owner.pem> \
    --guest-ssh-client-public-key <guest-ssh-client.pub> \
    --production-ssh-client-public-key <production-ssh-client.pub> \
    --guest-1-ssh-host-public-key <guest-1-ssh-host.pub> \
    --guest-2-ssh-host-public-key <guest-2-ssh-host.pub> \
    --guest-3-ssh-host-public-key <guest-3-ssh-host.pub> \
    --production-ssh-host-public-key <production-ssh-host.pub> \
    --release-evidence-public-key <release-evidence.pem> \
    --guest-ssh-private-key <mode-0600-dedicated-lab-key> \
    --request-dir <three-owner-signed-drill-envelopes> \
    --output-dir <new-private-evidence-directory>

Before execution, place every file argument and the request directory below a
canonical root-owned path whose complete parent chain is not group/world
writable. The dedicated lab SSH private key must be a root-owned, single-link
regular file with mode 0400 or 0600. The output directory must not exist and
its canonical parent must have the same root-trusted chain. The coordinator
uses the reviewed absolute `/usr/bin/ssh-keygen -y` to derive the private key's
Ed25519 public material and requires it to equal the normalized
`ssh-ed25519 <base64>` material in `--guest-ssh-client-public-key`. Its digest
must also equal the plan and isolation identities. A production key, a
different lab key, an unsafe mode/owner, or a writable parent fails before the
evidence directory or any guest is created.

The request directory contains exactly ssh-loss.envelope.json,
failed-health.envelope.json, and guest-reboot.envelope.json. Each is a
short-lived owner-signed promotion request bound to the plan's exact
predecessor, target, release paths, PM2 launcher, public URL, and 60-second
soak. The failed-health request must deterministically reach the control
plane's invalid_worker_completion recovery path; the coordinator does not
invent an unreviewed runtime mutation.

Execution is strictly sequential. The coordinator starts one guest unit,
constructs a private per-overlay known_hosts file from that guest's separately
validated, provision-bound lab host key, copies and re-verifies the exact
signed request, launches once, and polls the root control journal. It stops a
guest only after a terminal outcome is fully measured. If execution fails
after launch, it leaves that isolated guest running so the durable guest
recovery transaction can finish and does not start the next overlay.

Keep execution.json with all three outcome files. Each outcome binds the exact
receipt digest plus executionMode and testMode; the receipt binds the ordered
outcome payload digests, exact plan, normalized guest SSH client-key digest,
single-guest maximum, and completion time.
The evidence collect command requires --execution <execution.json>, revalidates
every bidirectional binding, and rejects testMode=true before creating a
machine-evidence directory. Verification requires the same canonical receipt
inside the bundle. Never copy only the three outcome files into an evidence
collection.

For guest-reboot, the first stop/start happens only after durable recovery
intent and predecessor-stop evidence. After recovered state and exact
predecessor health are proved, the coordinator performs a second clean reboot
and requires a third distinct boot ID, an unchanged terminal journal digest,
Result=success for nexus-release-promotion-recovery.service, an idle v3
control plane, exact PM2 runtime identity, and healthy application endpoints.
The 120-second target is measured from predecessor_stopped to the first
post-recovery service_healthy observation; the clean confirmation reboot does
not redefine that outage interval.

Retain bounded machine evidence under ignored .local/release paths. The
existing rollback-drill request builder and protected operational signer remain
the only path to a nexus.rollback-drill.v1 envelope. A VM boot or a signed
operator narrative is not drill evidence.
Unit tests use only fake binaries and explicitly marked test-mode execution.
Those tests prove sequencing and fail-closed parsing; they are not a substitute
for the real KVM, power-cut, systemd, PM2 cgroup, health, and second-reboot
evidence required before production promotion is unblocked.

Failure handling
----------------

An install or provision journal blocks every guest. A clean transactional
failure removes its own stage and journal. Guest runtime installation is also
journaled and recovered by the enabled guest recovery unit before SSH. A
readiness-collection journal is resumable and remains bound to the original
owner authorization and live measurement. A crash after immutable readiness
publication resumes by validating and promoting the exact pending evidence,
or by validating already-promoted evidence, before it removes the nonce-bound
handoff request. An unknown journal requires root inspection; do not delete it
merely to make the unit start.
Occupied loopback ports, unsafe ownership/modes, unknown files, a changed
signed digest, malformed Canonical metadata, a missing KVM device, or an
existing different active receipt all fail closed. A missing/spoofed/contended
shared-lock descriptor, host capacity below its floor, recent kernel OOM, or
unknown systemd state also fails closed.

This first version deliberately has no automatic guest deletion or replacement
command. Deprovisioning is a separate destructive owner action after evidence
retention and is not implied by installation or a completed drill.
